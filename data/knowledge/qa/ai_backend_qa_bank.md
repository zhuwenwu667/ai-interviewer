## Q01: Python 的 GIL 是什么？对多线程程序有什么影响？

- tags: python, 并发
- 答案要点：
  - GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器中的一把互斥锁，保证同一进程内同一时刻只有一个线程执行 Python 字节码。
  - 对 CPU 密集型任务，多线程无法真正利用多核并行，应使用多进程（multiprocessing）或 C 扩展释放 GIL。
  - 对 I/O 密集型任务影响小：线程在等待网络/磁盘 I/O 时会释放 GIL，因此多线程或 asyncio 仍能显著提升吞吐。
  - GIL 保护的是解释器内部状态（如引用计数），并不等于业务代码线程安全，共享数据的竞态仍需加锁。

## Q02: 可变默认参数为什么会有坑？如何规避？

- tags: python, 基础语法
- 答案要点：
  - 函数默认参数在函数定义时只求值一次，列表/字典等可变对象会被多次调用共享。
  - 典型现象：`def f(x, acc=[])` 多次调用累积上一次的数据。
  - 规避方式：默认值设为 None，函数体内 `if acc is None: acc = []`。
  - 本质是"定义时求值一次"与"调用时新建"的区别。

## Q03: 生成器（generator）是什么？相比列表有什么优势？

- tags: python, 迭代器
- 答案要点：
  - 使用 yield 的函数返回生成器对象，按需惰性产出元素，不一次性占用内存。
  - 适用于大文件逐行读取、流式数据处理、无限序列等场景。
  - 生成器是迭代器的一种，支持 next() 与 for 循环，但只能迭代一次。
  - 生成器表达式 `(x for x in ...)` 与列表推导式语法相似但语义不同。
  - 在 LLM 应用中，流式输出本质就是用异步生成器逐 token 产出。

## Q04: 深拷贝与浅拷贝的区别？

- tags: python, 数据模型
- 答案要点：
  - 浅拷贝（copy.copy、list[:]、dict()）创建新容器，但内部元素仍是原对象引用。
  - 深拷贝（copy.deepcopy）递归复制所有层级，新对象与原对象完全独立。
  - 对不可变元素（int/str/tuple）浅拷贝即可；嵌套可变结构且需要完全隔离时才需深拷贝。
  - deep copy 有循环引用处理，但成本高，需按场景选择。

## Q05: 协程相比多线程的优势是什么？asyncio 事件循环如何工作？

- tags: python, 异步, asyncio
- 答案要点：
  - 协程在用户态由事件循环调度，单线程内切换，无需 OS 线程切换与 GIL 竞争，可轻松支撑上万并发连接。
  - 事件循环维护就绪/等待中的任务，遇到 await 的 I/O 操作时挂起当前协程，I/O 就绪后通过回调唤醒。
  - 协程只在 I/O 等待处让出执行权，CPU 密集代码里 await 不会让出，会阻塞整个循环。
  - 协程里绝不能混用 requests、time.sleep 等阻塞调用，应使用 httpx、asyncio.sleep。
  - FastAPI 基于 ASGI + 事件循环，是 LLM API I/O 密集场景的高吞吐选择。

## Q06: asyncio.gather 和 asyncio.wait 有什么区别？

- tags: python, 异步, asyncio
- 答案要点：
  - gather 按输入顺序聚合所有协程结果，默认任一任务异常会向上抛出（其他任务不自动取消）。
  - return_exceptions=True 可让 gather 把异常作为结果返回，适合并发调用外部模型时部分失败仍需汇总的场景。
  - wait 返回 (done, pending) 两个任务集合，支持 FIRST_COMPLETED 等条件，控制更细。
  - 两者都要注意超时与取消语义，避免任务泄漏。

## Q07: Python 的垃圾回收机制是怎样的？

- tags: python, 内存管理
- 答案要点：
  - 主要靠引用计数：对象引用数归零立即回收，实时性好但无法处理循环引用。
  - 辅助以分代垃圾回收器（gc 模块），通过标记-清除处理容器对象间的循环引用，按三代策略降低扫描成本。
  - 实践建议：及时关闭文件/连接、对大对象显式 del 或用上下文管理器、避免全局容器无限增长导致内存泄漏。
  - __del__ 与循环引用组合曾有历史坑，资源释放推荐上下文管理器。

## Q08: 装饰器的原理是什么？functools.wraps 有什么作用？

- tags: python, 高级语法
- 答案要点：
  - 装饰器是接收函数并返回新函数的高阶函数，语法糖 @decorator 等价于 f = decorator(f)。
  - 常用于日志、计时、重试、缓存（@lru_cache）、权限校验等横切逻辑。
  - 不用 @wraps 会丢失原函数的 __name__、__doc__、类型签名，调试与文档生成异常。
  - 带参数装饰器实际是三层：外层接收参数、中层接收函数、内层执行逻辑。

## Q09: 多线程、多进程、协程分别适用于什么场景？

- tags: python, 并发
- 答案要点：
  - CPU 密集：多进程绕开 GIL 利用多核，如数值计算、批量解析。
  - I/O 密集且连接数多：协程（asyncio）资源开销最小，如同时调用多个 LLM/HTTP 接口。
  - I/O 密集且依赖阻塞库：多线程，如旧版 requests、文件操作。
  - 工程上常组合使用：FastAPI 处理网络 I/O 用协程，CPU 重任务丢到 ProcessPoolExecutor。

## Q10: 类型标注（type hints）在运行时有用吗？为什么仍推荐写？

- tags: python, 工程化
- 答案要点：
  - 默认情况下类型标注在运行时不做强制校验，错误类型不会因标注而自动报错。
  - 价值在于 IDE 补全与静态检查（mypy/pyright）、重构安全、自描述代码与团队协作。
  - Pydantic 利用标注在数据边界（API 入参、配置、LLM 结构化输出）做真正的运行时校验。
  - 配合 from __future__ import annotations 可让注解延迟求值，避免前向引用问题。

## Q11: MySQL 索引为什么能加速查询？B+ 树相比 B 树有什么优势？

- tags: 后端, mysql, 索引
- 答案要点：
  - 索引将全表扫描变为有序结构上的少量定位，B+ 树高度通常只有 3-4 层即可支撑千万级数据。
  - B+ 树只有叶子节点存数据，非叶子节点能容纳更多索引键，树更矮，磁盘 I/O 更少。
  - 叶子节点通过双向链表相连，天然高效支持范围查询与排序。
  - 聚簇索引叶子节点存整行数据，二级索引叶子节点存主键，需回表（覆盖索引可避免）。

## Q12: 什么是联合索引的最左前缀原则？

- tags: 后端, mysql, 索引
- 答案要点：
  - 对 (a, b, c) 联合索引，查询条件从最左列开始连续使用才能充分走索引。
  - where a=? and b=? 可用；where b=? and c=? 不能用该索引；where a=? and c=? 只用到 a 部分。
  - 范围查询（>、<、between、like 前缀）之后的列无法继续用于索引定位。
  - 索引列顺序设计通常按"等值高频列在前、范围列在后"并结合区分度考虑。

## Q13: 事务的四种隔离级别分别解决什么问题？

- tags: 后端, mysql, 事务
- 答案要点：
  - 读未提交：可能脏读、不可重复读、幻读，基本不用。
  - 读已提交（RC，Oracle 默认）：解决脏读，仍可能不可重复读、幻读；MySQL InnoDB 用 MVCC 实现。
  - 可重复读（RR，InnoDB 默认）：解决脏读、不可重复读，InnoDB 通过 MVCC + 间隙锁在很大程度上避免幻读。
  - 串行化：最严格，并发最低。
  - MVCC 通过 undo 版本链与 ReadView 让事务读到一致性快照。

## Q14: Redis 缓存穿透、击穿、雪崩的区别与解决方案？

- tags: 后端, redis, 高并发
- 答案要点：
  - 穿透：查询不存在的数据，请求全打到数据库。方案：缓存空值（短 TTL）、布隆过滤器。
  - 击穿：单个热点 key 过期瞬间大量并发打库。方案：互斥锁重建、逻辑过期、热点不过期。
  - 雪崩：大量 key 同时过期或 Redis 宕机。方案：TTL 加随机抖动、多级缓存、集群高可用、限流降级。
  - 三者都要配合限流与兜底，避免数据库被打垮。

## Q15: Redis 分布式锁要注意什么？RedLock 有什么争议？

- tags: 后端, redis, 分布式
- 答案要点：
  - 基础实现：SET key value NX PX timeout，value 用唯一标识，释放时用 Lua 脚本校验后再删，避免误删他人的锁。
  - 必须设过期时间防死锁；业务执行时间可能超过 TTL 时需要看门狗续期。
  - 主从异步复制下故障切换可能导致锁丢失，它不是严格意义的强一致锁。
  - RedLock 通过多数节点加锁提高安全性，但 Martin Kleppmann 与 antirez 有著名争论；对强一致要求应选 ZooKeeper/etcd。

## Q16: 如何保证消息队列消费的幂等性？

- tags: 后端, kafka, 可靠性
- 答案要点：
  - MQ 普遍提供至少一次（at-least-once）投递，重复消息是常态，幂等要在业务侧保证。
  - 常用手段：唯一业务 ID + 去重表/Redis SETNX、状态机只允许合法流转、数据库唯一索引、乐观锁版本号。
  - 本地消息表 + 对账可保证最终一致；消费与落库尽量在一个事务边界内设计。
  - 订单场景的幂等键（客户端生成 requestId）是同一思路在 HTTP 接口上的应用。

## Q17: CAP 理论是什么？为什么注册中心常选 AP 或 CP？

- tags: 后端, 分布式
- 答案要点：
  - CAP：一致性（C）、可用性（A）、分区容错（P）三者在网络分区时不可兼得，P 在分布式系统中必然存在，实际是 C 与 A 的取舍。
  - CP 系统（etcd/ZooKeeper）分区时拒绝部分请求保一致，适合配置、锁、选主。
  - AP 系统（Eureka 早期设计）分区时仍返回可能过时的数据保可用，适合服务发现。
  - 不要脱离场景谈选型，并注意 PACELC 中即使无分区也存在延迟与一致性的权衡。

## Q18: 常见限流算法有哪些？优缺点是什么？

- tags: 后端, 高并发, 算法
- 答案要点：
  - 固定窗口：实现简单，但窗口边界有 2 倍突刺问题。
  - 滑动窗口：平滑边界问题，Redis ZSet 可实现，内存成本稍高。
  - 漏桶：恒定速率出水，平滑流量但无法应对合理突发。
  - 令牌桶：桶中攒令牌，允许一定突发，最常用（Nginx limit_req、Guava RateLimiter）。
  - 分布式限流可用 Lua 脚本把"取令牌+记录"做成原子操作。

## Q19: JWT 的结构与优缺点？如何解决注销问题？

- tags: 后端, 安全, 鉴权
- 答案要点：
  - JWT 由 Header、Payload、Signature 三部分 Base64URL 拼接，服务端用密钥验签，无需服务端会话存储。
  - Payload 仅编码不加密，不能放敏感信息；应设置较短过期时间。
  - 无状态带来难注销问题：方案有黑名单（Redis 存到过期）、短 access token + 长 refresh token、版本号机制。
  - 还要防算法混淆攻击（强制指定算法）、密钥泄露与重放。

## Q20: Docker 镜像如何优化体积与构建速度？

- tags: 后端, docker, 部署
- 答案要点：
  - 选精简基础镜像（python:3.11-slim），多阶段构建把编译依赖与运行时分离。
  - 合理利用层缓存：变化少的依赖安装层在前，COPY 源码在后；先拷 pyproject/lock 文件安装依赖。
  - 用 .dockerignore 排除 .venv、.git、缓存目录；编译后清理 apt/pip 缓存。
  - 容器以非 root 运行，配置 healthcheck；compose 中用 depends_on + condition 控制启动顺序。

## Q21: Token 是什么？为什么 LLM 按 token 计费而不是按字？

- tags: llm, 基础概念
- 答案要点：
  - Token 是模型分词器（tokenizer）切出的最小单位，可能是子词、词或标点；中文常 1-2 个汉字对应 1 个多 token。
  - 模型在 token 空间上做嵌入与预测，上下文窗口、计费、生成都以 token 计。
  - 同样字数的中英混合文本 token 数不同，做成本估算要用 tiktoken 等工具实测。
  - RAG 上下文管理本质是在 token 预算内分配"系统指令/检索证据/历史/当前问题"。

## Q22: temperature、top_p、frequency_penalty 分别如何影响输出？

- tags: llm, 参数
- 答案要点：
  - temperature 对 logits 做缩放后采样，越高分布越平坦、越发散；越低越确定，评分/抽取场景应调低（如 0.1-0.3）。
  - top_p（nucleus sampling）只在累计概率达到 p 的最小候选集中采样，控制长尾。
  - temperature 与 top_p 通常只调一个，避免双重裁剪难预测。
  - frequency_penalty/presence_penalty 惩罚已出现 token，用于减少重复、鼓励换话题，面试问答出题时可轻度使用。

## Q23: 什么是大模型幻觉？RAG 中如何系统性缓解？

- tags: llm, 幻觉, rag
- 答案要点：
  - 幻觉指模型生成流畅但不符合事实或无依据的内容，根源是概率建模、训练知识陈旧与上下文缺失。
  - 缓解手段：RAG 提供权威上下文并要求"仅依据材料作答"、降低 temperature、要求引用来源。
  - 输出后用 faithfulness 指标（答案能否由上下文推出）做自动评测与人工抽检。
  - 检索不到时让模型显式表达"知识库未提及"而非强答；对高风险场景加规则/工具校验。

## Q24: 什么是 Function Calling？它是模型真的执行了函数吗？

- tags: llm, agent, function-calling
- 答案要点：
  - 不是。模型根据函数 schema 输出结构化的调用意图（函数名 + JSON 参数），真正的执行由应用代码完成。
  - 应用执行后把结果作为 tool 角色消息回传，模型再据此生成最终回答，构成 ReAct 的工具闭环。
  - 价值：把不确定的自然语言约束为可校验的结构化输出，是 Agent 连接外部系统的桥梁。
  - 参数必须做服务端校验与权限控制，不能信任模型生成的入参（如 SQL、文件路径）。

## Q25: Prompt Engineering 有哪些经过验证的有效技巧？

- tags: llm, prompt
- 答案要点：
  - 明确角色、任务与输出格式；复杂任务给 1-3 个高质量示例（few-shot）。
  - 让模型"一步步思考"（chain-of-thought）或先规划再执行；要求结构化/JSON 输出并给 schema。
  - 把长指令拆成系统/用户/工具消息分层，相关信息置于上下文首尾（lost-in-the-middle 效应）。
  - 用约束与拒答规则兜底；prompt 改动应配套评测集回归，而非凭单次效果拍板。

## Q26: 上下文窗口受限会带来哪些工程问题？怎么解决？

- tags: llm, 上下文, rag
- 答案要点：
  - 超长文档/历史塞不进去，超窗会报错或被截断；中间位置信息容易被忽略。
  - 解决：RAG 只召回相关片段替代全文；历史对话做摘要压缩或滑动窗口；map-reduce 分段处理长文档。
  - 精确做 token 预算管理：预留输出 token，按预算裁剪证据条数。
  - 还可用长上下文模型兜底，但成本与延迟更高、且不解决相关性问题。

## Q27: 为什么 LLM 输出普遍采用流式（SSE/WebSocket）？

- tags: llm, 后端, sse
- 答案要点：
  - LLM 自回归逐 token 生成，完整响应常需数秒到数十秒，等全部生成完再返回用户体验差。
  - SSE（Server-Sent Events）基于 HTTP 单向推送，实现简单、天然适合服务端推 token；双向交互才需要 WebSocket。
  - FastAPI 用 StreamingResponse + async generator 即可输出 text/event-stream。
  - 流式要额外处理中途异常（error 事件）、断线与重试，以及在首 token 前先推送阶段事件（如"检索中"）。

## Q28: Embedding（句向量）的原理是什么？余弦相似度为何衡量语义相近？

- tags: llm, embedding, 检索
- 答案要点：
  - Embedding 模型把文本映射为固定维度稠密向量，训练目标让语义相近的文本在向量空间中距离更近。
  - 余弦相似度衡量两向量夹角，只看方向不看模长，对文本长度差异更鲁棒。
  - bge-m3 等模型支持多语言与长文本，输出归一化后点积即余弦相似度。
  - Embedding 是语义模糊匹配，对精确关键词（错误码、型号）不敏感，需要 BM25 互补。

## Q29: RAG、微调（SFT）、提示工程三者如何取舍？

- tags: llm, rag, 微调
- 答案要点：
  - 知识更新频繁、需要溯源、数据量大：优先 RAG，成本低且可随时更新知识库。
  - 需要改变模型稳定的行为风格、输出格式或领域表达能力：考虑 SFT/LoRA。
  - 简单任务先用提示工程（含 few-shot）验证，复杂度递增而非一上来微调。
  - 三者可组合：微调让模型"会用 RAG、听话"，RAG 提供"实时事实"。

## Q30: 如何评测一个 LLM 应用的质量？

- tags: llm, 评测, ragas
- 答案要点：
  - 分层评测：组件级（检索命中率/召回率、rerank 排序）、回答级（忠实度、相关性）、端到端任务成功率与人工评分。
  - 自动指标可用 RAGAS（faithfulness、context precision/recall、answer relevancy）与 LLM-as-a-judge，但评委模型自身有偏见需校准。
  - 必须建固定评测集并纳入 CI 回归，记录基线，防止改 prompt/参数引入退化。
  - 线上看业务指标（采纳率、转人工率）与bad case 回流，形成闭环。

## Q31: 完整的高级 RAG 管线包含哪些环节？

- tags: rag, 架构
- 答案要点：
  - 离线侧：文档解析 → 清洗 → 结构化切块（保留标题层级）→ Embedding → 写入向量库，同时建 BM25 索引。
  - 在线侧：查询改写 → 向量+BM25 混合召回 → RRF 融合 → Rerank 精排 → 上下文组装 → 受控生成（引用、拒答）。
  - 增强层：Agentic RAG 检索质量自评与重检索、多路召回、查询路由、证据去重。
  - 保障层：评测集与指标、链路追踪、缓存、降级。

## Q32: RAG 切块（chunking）策略有哪些？太大太小各有什么问题？

- tags: rag, chunking
- 答案要点：
  - 块太大：主题不聚焦、向量表征被稀释、占用 token 预算多、定位证据粗糙。
  - 块太小：上下文不完整、语义破碎，模型拿到只言片语无法回答。
  - 常见策略：固定大小+重叠、按标题结构切、按语义切分；父子文档（小块检索、大块喂模型）兼顾定位与上下文。
  - 切块要保留标题、来源等元数据，并按文档类型调参；改策略后必须重跑评测对比。

## Q33: 为什么需要混合检索（向量 + BM25）？

- tags: rag, 混合检索, bm25
- 答案要点：
  - 向量检索擅长语义相近但用词不同的查询（"电脑变慢" 命中 "计算机性能问题"），弱点是精确符号、罕见词、数字编号。
  - BM25 基于词项匹配与 IDF 权重，对专有名词、错误码、型号、人名等精确匹配强，但不懂同义改写。
  - 两路召回互补，再用 RRF 融合与 Rerank 精排，实践中几乎总是优于单路向量。
  - 中文 BM25 要先分词（jieba 等），否则按字匹配噪声较大。

## Q34: RRF（Reciprocal Rank Fusion）的原理与优点？

- tags: rag, rrf, 排序融合
- 答案要点：
  - 公式：score(d) = Σ 1/(k + rank_i(d))，对每路排名取倒数（k 常取 60）后求和。
  - 只依赖排名而非各路原始分，天然解决向量余弦分与 BM25 分尺度不可比的问题。
  - 实现简单、无需训练、对异常分值鲁棒，是工业界融合多路召回最常用的基线方法。
  - k 越大，头部和尾部的权重差异越平缓；调参后仍需 Rerank 做语义精排。

## Q35: Rerank（重排）和向量检索的区别是什么？为什么能提升效果？

- tags: rag, rerank
- 答案要点：
  - 向量检索是"查询-文档"双塔独立编码后算相似度，速度快但两者没有交互，是粗排。
  - Reranker（如 bge-reranker）把 query 与每个候选拼接后用交叉编码器联合建模，捕获细粒度交互，准但算力贵。
  - 工程上先用向量/BM25 从海量文档粗召回几十条，再只对这几十条做 rerank 精排取 Top-K，兼顾效果与成本。
  - 这也是"召回追求高 recall，精排追求高 precision"的典型两阶段架构。

## Q36: HNSW 向量索引的原理？关键参数如何权衡？

- tags: rag, 向量数据库, hnsw
- 答案要点：
  - HNSW（分层可导航小世界图）把向量组织成多层近邻图，查询从顶层稀疏节点逐层下降，近似最近邻搜索复杂度近对数级。
  - M 控制每层每个节点的最大边数：越大召回越高、内存与建索引成本越高。
  - efConstruct 影响建图质量，efSearch 影响查询时搜索宽度：越大越精确但越慢。
  - 它是 ANN 近似算法，牺牲少量召回换巨大性能提升；可用量化（PQ/SQ）进一步压缩内存。

## Q37: 什么是 Agentic RAG？相比固定管线强在哪里？

- tags: rag, agent, agentic-rag
- 答案要点：
  - 固定管线对任何问题都走同样的检索-生成流程；Agentic RAG 让 LLM 作为决策者参与检索过程。
  - 典型循环：检索 → LLM 评估证据是否充分 → 不足则改写查询、换知识库或扩大召回再检索，设最大轮次兜底。
  - 还可做查询路由（FAQ/图谱/SQL/网页）、多跳推理中的迭代检索、检索结果去重与综合。
  - 代价是更多 LLM 调用与延迟，需要评估轮次、记录决策日志并设终止条件，避免无限循环与成本失控。

## Q38: ReAct 模式的原理与局限是什么？

- tags: agent, react
- 答案要点：
  - ReAct = Reasoning + Acting，模型交替产出"思考（Thought）→ 行动（Action/工具调用）→ 观察（Observation）"直至给出答案。
  - 优点：把推理与工具使用结合，行为可解释，能用搜索/计算器/数据库补足模型自身能力。
  - 局限：线性单链路、容易在多步中累积错误、缺乏全局规划与回滚；循环次数与成本需要硬约束。
  - 复杂流程更适合用显式状态机（如 LangGraph）把分支、人工介入、中断恢复工程化。

## Q39: 为什么用 LangGraph 而不是裸 ReAct 或一串 if-else？

- tags: agent, langgraph, 状态机
- 答案要点：
  - LangGraph 把 Agent 建模为显式状态图：节点是处理步骤，边是确定性或 LLM 驱动的条件路由，状态在图中流转并可持久化（checkpoint）。
  - 支持循环、分支、并行、人工审批节点与中断恢复，适合"出题-回答-追问-评分"这类有阶段、有轮次约束的业务。
  - checkpoint 机制让会话可从中断点继续，比内存态 ReAct 更适合生产。
  - 边界仍由代码控制，避免纯自主 Agent 的不可控行为；简单线性任务用它则属于过度设计。

## Q40: RAGAS 四个核心指标分别在衡量什么？

- tags: rag, ragas, 评测
- 答案要点：
  - Faithfulness（忠实度）：答案中的陈述能否由检索上下文推出，衡量幻觉，最重要的安全指标。
  - Answer Relevancy（答案相关性）：答案是否切题、有无答非所问或冗余。
  - Context Precision（上下文精确率）：召回的相关证据是否排在前面、噪声占比，反映 rerank 质量。
  - Context Recall（上下文召回率）：标准答案所需信息是否都被检索到，反映召回完整性。
  - 注意 RAGAS 依赖评委 LLM，分数受评委模型、样本构造与语言影响，应固定条件做相对比较并结合人工抽检。
