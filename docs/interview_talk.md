# AI 模拟面试官 · 面试讲解材料

> 面向「AI 应用开发 / 大模型后端」岗位的自述稿与追问应答要点。
> 配合仓库代码与 `data/eval/baseline.json` 使用；所有数字均为本项目真实跑出的结果。

---

## 1. 一分钟电梯陈述

「我做了一个 AI 模拟面试官：候选人上传简历和目标岗位 JD，系统扮演面试官，出题 → 等作答 →
打分 → 追问 → 最后给一份带雷达图和改进建议的报告。它的核心不是调 API，而是把 **RAG 检索质量**
和 **Agent 流程可控性**这两件事做扎实：检索用查询改写 + 向量/BM25 混合召回 + RRF 融合 + Rerank 精排，
并在上下文不足时让模型自评、自动改写重检索；流程用 LangGraph 显式状态机编排，
可恢复、可测试。我用 RAGAS 建了 43 条离线评测集做回归，faithfulness 0.985、context_recall 1.0，
题库外诱导题拒答率 100% 且非诱导题零误拒答。整套东西用 Docker Compose 三容器一键部署。」

---

## 2. 项目背景

- **痛点**：真实面试准备缺「能追问的陪练」；通用大模型直接问答会编造（幻觉），也无法依据候选人自己的
  简历/目标 JD 提问，答完没有结构化反馈。
- **目标**：把「简历 + JD + 八股题库」作为**可溯源知识库**，让每个问题/反馈都能引用来源；
  面试官行为要**稳定可复现**（不能每次流程都不一样）；效果要**可量化**（有指标、有回归）。
- **边界**：单机演示规模（2C4G），知识库为示例数据；重点在工程架构与质量闭环，不在模型训练。

## 3. 核心难点

1. **检索「有答案但没召回」**：单轮向量检索对精确关键词（错误码、型号）不敏感，且一次没召回到就直接答错。
2. **多路召回分数不可比**：向量余弦分与 BM25 分尺度不同，直接加权求和需要调参且不稳定。
3. **Agent 流程可控性**：若用裸 ReAct 让模型自由决定下一步，面试流程会发散、不可复现、难以测试。
4. **幻觉与拒答的平衡**：既要「仅依据材料作答」，又要在题库外问题（如「CEO 星座」）上**明确拒答**，
   同时**不能**把长而正确的答案误判为拒答。
5. **可观测与评测**：多节点链路出问题难定位；LLM 类系统必须能回答「改了什么、效果涨了还是跌了」。

## 4. 方案（分层讲）

**4.1 数据层**：文档加载（PDF/MD/TXT）→ 保留标题层级切块（chunk_size 500 / overlap 80，句号边界回退）
→ 确定性 chunk_id → Qdrant 幂等 upsert（重建时按 source 删除旧点，规避 local 模式「同名集合重建数据复活」的坑）。
知识库分 `resume` / `jd` / `qa` 三类，支持上传动态扩充。

**4.2 检索层（这是重点）**：
- **查询改写**：Multi-Query 一次生成 3 条改写（原查询居首，共 4 路向量召回）；HyDE 可选（生成假设答案再检索）。
  LLM 失败时降级不中断。
- **双路召回**：向量路（Qdrant，含 `kb_type` 过滤）+ BM25 路（rank-bm25 + jieba，heading+text 参与打分）。
- **RRF 融合**（`score(d)=Σ 1/(k+rank)`，k=60）：只依赖排名、免训练，天然解决尺度不可比。
- **Rerank 精排**：融合后取 `max(4*top_k,20)` 候选交 bge-reranker 交叉编码器，取 Top-K（默认 6）。

**4.3 Agentic RAG（自适应检索）**：每轮召回后，LLM 依据「问题 + Top-3 上下文摘要」判定是否 `sufficient`；
不足则基于反馈改写查询重跑（默认最多 2 轮），并返回各轮中 Top-1 rerank 分数**最优**的那一轮。防御：
最大轮数上限、非法输出重试一次后**保守放行**、调用异常也不中断主流程。

**4.4 Agent 编排（LangGraph）**：7 个节点 `greeting / ask_question / receive_answer / assess_answer /
followup / final_evaluation / report`，用条件边路由：
`assess_answer` 后 → `followup`（质量 partial/poor 且未超追问上限）/ `next`（下一题）/ `finish`（答满）。
状态快照持久化到 SQLite，支持进程重启后**恢复会话**。

**4.5 服务层**：FastAPI，`POST /sessions/{id}/messages` 用 **SSE** 逐 token 推送面试官文本；
统一异常 → 中文可读 `error` 事件，不断连接；`/health` 做组件级探活（配置 + Qdrant 连通）。

**4.6 可观测**：统一 `SpanRecord`（trace/span/parent/kind/耗时/字段），以上下文管理器和装饰器**零侵入**埋点；
配 Langfuse 就上报（一个 `trace_id`=会话 ID 串起全链路），没配就写本地 `logs/traces.jsonl`，字段结构一致。

**4.7 评测**：43 条评测集（简历 10 / JD 10 / 题库 16 / 题库外诱导 7），RAGAS 四指标 +
检索命中率 + 拒答率；固定 judge 模型与 `temperature=0`、`max_tokens=4096`；`scripts/run_eval.py` 一键出报告。
另有 `scripts/run_ablation.py`（检索管线 5 档消融）、`scripts/measure_session_cost.py`（真实会话成本/延迟实测）
与 `scripts/run_judge_cross_check.py`（异源 judge 交叉验证，量化自评偏置，见 §5.3）。
Judge 可切换：`EVAL_JUDGE_MODEL / EVAL_JUDGE_BASE_URL / EVAL_JUDGE_API_KEY`，留空回落 DeepSeek。

## 5. 量化效果（真实基线；2026-10-16 首轮，2026-10-18 复跑）

最新复跑（`data/eval/reports/eval_20261018_021445.{md,json}`，43 条）：

| 指标 | 得分 | 阈值 |
| --- | --- | --- |
| faithfulness | 0.989 | 0.85 ✅ |
| context_recall | 0.993 | 0.80 ✅ |
| answer_relevancy | 0.895 | 0.85 ✅ |
| context_precision | 0.940 | 观察项 |

（2026-10-16 首轮对应值为 0.985 / 1.000 / 0.872 / 0.912，档间差异属生成随机性。）

- 期望来源**命中率 100%**（二值），平均上下文 6.0 条，平均自适应轮数 **1.58**；
  **来源精确率 P 0.861 / 召回 R 1.000 / F1 0.907**（见 §5.4，二值命中率已饱和、无区分度）。
- 题库外诱导题**拒答率 100%**（目标 ≥80%），非诱导题**误拒答率 0%**。
- 工程侧：离线单测 **147 例全绿**（另 1 例因缺 `langfuse` 跳过；含集成共 151 例）、覆盖率核心模块 ≥70%；三容器部署健康检查全通过。
- 注意：`answer_relevancy` 对 judge 选择较敏感（自评比异源 judge 高约 0.11，见 §5.3），
  它的绝对值当**趋势信号**看，不作为硬门槛单独宣传。

### 5.1 检索消融：各组件的边际贡献（同一 43 条评测集，2026-10-17）

固定生成与评判参数，只逐档叠加检索组件（`scripts/run_ablation.py`）：

| 档位 | context_precision | 每问耗时(s) | 成本(元/问) |
| --- | --- | --- | --- |
| dense（仅向量） | 0.819 | 0.31 | ¥0.0025 |
| +bm25（朴素拼接融合） | 0.824 | 0.36 | ¥0.0025 |
| **+RRF** | **0.925** | 0.45 | ¥0.0026 |
| +rerank | 0.935 | 0.38 | ¥0.0027 |
| +agentic（改写 + 自评重检索） | 0.937 | 2.28 | ¥0.0058 |

**一句话结论（这是面试要讲的重点）**：本场景 `context_precision` 的收益主要来自 **RRF 融合排序**
（0.824 → 0.925，相对 +12%），而不是「多一路 BM25 召回」（+0.005）或「精排」（+0.010）；
而 **agentic 档在这份评测集上边际收益为负**（+0.002，却 6× 耗时、2.2× 成本），
它的价值是覆盖评测集测不到的「首轮召回失败」——属于**鲁棒性冗余，不是精度提升**，
所以它是「上线取舍」而非「评测结论」。来源命中率各档均 100%，说明评测集对检索变体已饱和，
这也是改用 `context_precision` 作主信号的原因；该饱和问题另在 §5.4 用来源 P/R/F1 做了缓解
（二值 100% 掩盖了 JD 类问题真实 P=0.5）。

### 5.2 真实面试成本与延迟（6 场 × 5 题，真实模型，2026-10-17）

| 指标 | 实测 |
| --- | --- |
| 单场 token | 12.8k – 16.5k |
| 单场成本（deepseek-chat 全价） | 均值 **¥0.052**（区间 ¥0.046–¥0.060） |
| 单场端到端耗时 | 均值 **48.7s**（P50 48.9s / 最大 51.3s） |
| 单轮成本（6 轮/场） | ≈ **¥0.0087** |
| 出题阶段 `ask_question` | 均值 **10.7s**（P95 11.8s）← 首字延迟大头 |
| 终评报告 `report` | 均值 7.1s |
| 单次 LLM 调用 / 单次 rerank | 1.42s / 0.46s |

**一句话结论**：一场 5 题真实面试全价**约 5 分钱**——「重检索 + 重评判」的架构成本完全可承受；
延迟瓶颈是出题阶段的**串行 LLM 与 embedding 往返**（改写 + 多路嵌入 + 生成），不是向量库，
所以提速优先级是「并发改写/嵌入 + 缓存改写结果」，而不是换向量库。

### 5.3 Judge 自评偏置治理：异源 judge 交叉验证（同一 36 条生成结果，2026-10-18）

**痛点**：上面所有指标都是 LLM-as-judge，而默认 judge（`deepseek-chat`）和线上打分模型**同源**，
会被问「是不是自己给自己打高分」。**做法**：不重新生成答案，把**同一批 36 条生成结果**（144 个指标单元，0 缺失）
交给两个 judge 各打一遍——自评 `deepseek-chat` vs 异源 `Qwen/Qwen2.5-72B-Instruct`
（另一厂商 SiliconFlow + 另一模型族，Δ = 自评 − 异源，>0 表示自评偏高）。

| 指标 | Δ(自评−异源) | ≤0.10 一致率 | Pearson |
| --- | --- | --- | --- |
| faithfulness | **-0.027** | 88.9% | — |
| context_precision | **+0.015** | 91.7% | 0.866 |
| context_recall | **0.000** | 100.0% | — |
| answer_relevancy | **+0.108** | 55.6% | 0.638 |

全体 144 个单元：|Δ|≤0.10 一致率 **84.0%**（≤0.20 为 93.8%）。

**一句话结论（诚实版）**：`faithfulness` / `context_precision` / `context_recall` **对换 judge 稳健**，
说明这几项没有被自评模型抬高；但 **`answer_relevancy` 自评偏高 0.108、逐条一致率仅 55.6%**，
它对 judge 切题判准更敏感（依赖「人造问题 + embedding 相似度」），所以它的**绝对值要克制解读**，当趋势信号用。
配套做了可切换的独立 judge 配置 `EVAL_JUDGE_*`（留空回落 DeepSeek，线上零变化）——
既能做交叉验证，也不污染生产链路。

### 5.4 引用质量度量：从二值「来源命中率」升级为 P/R/F1（2026-10-18）

**痛点**：原来的「来源命中率」是二值指标（召回里有一个是期望来源就算命中），在本评测集上
**恒为 100%、早已饱和**，既区分不了检索策略，也说不清「召回的证据是否精准」。
**做法**：改成按来源粒度算 precision / recall / F1，并加一个诊断项「答案显式引用标记率」。

| 指标 | 数值 |
| --- | --- |
| 来源命中率（二值） | 100.0%（已饱和） |
| 来源精确率 P | **0.861** |
| 来源召回率 R | **1.000** |
| 来源 F1 | 0.907 |
| 答案显式引用标记率 | **22.2%**（8/36） |

**一句话结论（诚实版，必须讲到局限）**：新指标比二值命中率**有区分度**——`resume` / `qa` 两类 P=1.000，
只有 `jd` 类是 **0.500**，因为 JD 问题只把中文 JD 列为期望来源，而检索**合理地**同时召回了同一份 JD 的
**英文版**。所以 **JD 的 P=0.5 是「期望集口径偏严」，不是检索错误**：单期望来源的数据集会低估真实检索质量。
改进方向是允许「同题多文件」或改用品级相关度；这一局限我**如实披露**，不粉饰。
另外答案只有 22.2% 自带引用标记，说明生成结果并不产出可校验的行内引用，
所以引用质量**只能在检索侧度量**——这也是为什么要把口径说清楚，而不是叫「citation accuracy」。

### 5.5 评测回归门禁：阈值跌出即构建失败（2026-10-18）

**痛点**：上面这些指标是「某一次跑出来的」，靠人记、靠报告——下次改动让指标跌了，没人会发现。
**做法**：把评测结论固化成**门禁**（`app/eval/gate.py` + `scripts/check_eval_gate.py`），CI 里做**确定性校验**：
① 门槛指标达标（`faithfulness`/`context_recall`/`answer_relevancy`）；② 诱导题拒答率 ≥80%；
③ 无执行失败样例；④ 相对基线跌幅 ≤0.05。任一不过即**非零退出、构建失败**。
**关键取舍**：**不在 CI 里重跑 RAGAS**——它要密钥、有真实费用、约 7 分钟且受 TPM 限速；所以把评测当作
**发布前手动步骤**（报告入库），CI 只做**秒级、无密钥、可复现**的**报告校验**。门禁要的是确定性与可控成本。
**实测**：最新报告 `check_eval_gate.py` → 通过 ✅、退出码 0；把容忍度收到 `--max-drop 0.001`，
立刻抓到 `context_recall 1.0000 → 0.9931`（跌 0.0069 > 0.001）→ 未通过 ❌、退出码 2——门禁真的会拦。
CI（`.github/workflows/ci.yml`，push/PR 触发、无需密钥）：`ruff check` → `pytest -m "not integration"`
（147 passed / 1 skipped）→ `check_eval_gate.py`。

### 5.6 语义缓存：把重复出题的检索管线整体跳过（2026-10-18）

**痛点**：5.2 实测把瓶颈定位到 `ask_question`（10.7s）——每问要走「查询改写 LLM → 向量化 → 双路召回 →
精排 → 充足性自评」约 6 次 LLM 往返；5.1 又显示自适应管线**几乎每次都跑满重写轮数**（54 rewrite / 18 出题 = 3.0 次/题），
也就是这套昂贵管线在**同一查询上被反复执行**。
**做法**：给检索加**查询级语义缓存**（`app/rag/cache.py`），命中即**整体跳过**整条管线：
① **复用已有 Qdrant**（新增集合 `{collection}__semantic_cache`、共用同一客户端），不引入 Redis；
② 命中判定为查询向量**余弦相似度 ≥0.95**，`scope`（`kb_types|top_k`）过滤避免跨范围污染；
③ 结果带 **TTL 1800s**，且**知识库摄入/上传后自动清空**；④ 缓存**整包检索结果**（无损序列化往返，有单测），命中即重放。
**实测（同一批真实面试，仅缓存开关不同）**：`ask_question` 平均 **9194.1ms → 3182.2ms（-65.4%）**（P50 9110.8→1720.7ms）；
单场总耗时 **43.65s → 25.84s（-40.8%）**；单场成本 **¥0.0529 → ¥0.0377（-28.7%）**；
LLM 调用 **174 → 90（-48.3%）**、总 token **86847 → 59654（-31.3%）**；rewrite 调用 **54 → 12**、rerank **54 → 12**。
缓存自身 18 次查询命中 14 次、命中率 **0.778**（4 次未命中 = 4 个不同 track 首次出现）；两遍作答均分区间一致，**出题质量未退化**。
**关键取舍**：**复用 Qdrant 而非引入 Redis**——检索结果本就以向量躺在 Qdrant，命中判定天然是一次相似度查询，
单独拉 Redis 属过度工程；**缓存整包结果而非只缓存 embedding**——真正贵的是改写/自评两个 LLM，只缓存 embedding 省不到大头。

## 6. 复盘

- **做对了**：把「检索质量」当成一等公民（混合检索 + 自适应 + 评测闭环），而不是只拼 prompt；
  Agent 流程显式状态机而非自由循环；埋点零侵入，调试成本低。

### 6.1 故障复盘（5 篇）

**① Qdrant local 模式「已删数据复活」**
现象：知识点重跑摄入后，检索命中已被替换的旧内容，同一 source 出现重复点。
根因：local 文件模式下按「整集合重建」清理，但磁盘上旧 segment 未被真正回收，客户端重载时又把旧向量读了回来。
修复：改为**按 payload 过滤删点**（`delete by filter: source`）而非删集合；上传文件统一用
`source=uploads/{session_id}/...` 精确溯源清理，评测/部署切 server 模式用命名卷持久化。教训：把「删除」当成业务语义（按 source），不要依赖存储层的物理删除时机。

**② RAGAS 0.4.x 依赖地震**
现象：评测脚本 import 失败——`vertexai` 模块在新版被移除，且 `langchain-community` 版本冲突。
根因：RAGAS 0.4 系列只支持**新版 instructor 工厂接口**，旧的 `aevaluate`/LangChain wrapper 被拒；0.4.3 又引用了已移除的 vertexai。
修复：锁定 `ragas==0.4.1` + `langchain-community==0.4.1`，judge 用 instructor 工厂构造。教训：评测框架的「最新版」往往是坑，版本要钉死在 lock 里并写进 CI。

**③ `uv.lock` 绝对直链导致国内构建超时**
现象：Docker 构建阶段 `uv sync --frozen` 卡约 7 分钟后失败，所有包直连 `files.pythonhosted.org` 超时。
根因：lock 里记录了每个 wheel 的**绝对 URL**，`--frozen` 严格按 lock 直链下载，**完全绕过** `UV_INDEX_URL` 镜像设置。
修复：Dockerfile 在构建期把 lock 中 `files.pythonhosted.org` 批量重写为国内镜像 host 后再 sync。教训：「配了镜像」不等于「走了镜像」——lock 里的直链要单独处理。

**④ git push/fetch 的 HTTP/2 抖动**
现象：本地 push 与服务器 clone/fetch 频繁失败（`RPC failed` / `unexpected eof` / 大仓超时）。
根因：跨境网络下 HTTP/2 多路复用易受丢包影响，长连接中断。
修复：本地 push 用 `git -c http.version=HTTP/1.1 push`；服务器用 `fetch --depth 1` 重试后 `reset --hard origin/main`；clone 前先切 HTTP/1.1。教训：把「部署脚本」写活——重试与降级协议是常态，不是偶发。

**⑤ 跨厂商 judge 的 TPM 限流「越重试越糟」**
现象：异源 judge（SiliconFlow Qwen2.5-72B）在并发 2–8 时大量 `429 TPM limit reached`，评测单元格缺分。
根因：TPM 是**按分钟**计 token，而重试会**重发整段 prompt**——重试越多、越把配额烧在重复内容上，形成恶化循环；
并发只是把突发量进一步推高。
修复：**先用小请求实测出可持续节奏**，再据此把并发降到 **1（串行）**、并对限流失败做指数退避；串行后 0 失败、0 限流、
144 格全满。教训：面对限流，**降并发 + 控节奏**比「加并发 + 加重试」有效；重试要判断「重发是否放大配额消耗」。

## 7. 高频追问 14 问

**Q1：为什么用 RRF，不用加权求和？**
因为两路分数尺度不可比——向量余弦相似度在 [0,1] 且分布集中，BM25 是未归一化的词频分数。
加权求和要先归一化再调权重，换数据集/换模型就得重调；RRF 只看排名，天然尺度无关、免训练、对异常分值鲁棒，
是工业界融合多路召回最稳的基线。k 越大头部越平缓，我们取常规的 60。

**Q2：Multi-Query 改写会不会引入噪声甚至幻觉？**
有两个约束：一是原查询始终居首并保留，改写是「补充召回」不是「替代」；二是最终有 Rerank 交叉编码器
按 query 相关性精排，无关改写召回的文档会被压下去。并且 LLM 改写失败时直接降级用原查询，不阻塞主流程。

**Q3：自适应重检索怎么防止死循环或越改越差？**
三层防御：① 硬上限 `max_rewrite_rounds`（默认 2，即最多 3 次检索）；② 评估输出非法（解析不出 yes/no）时
重试一次后**保守放行**，避免因解析噪声反复重搜；③ 达上限时**返回各轮 Top-1 rerank 分数最优的那一轮**，
而不是用最后一轮——保证重检索是「择优」而非「最后一次覆盖」。

**Q4：中文 BM25 怎么分词的？为什么这么做？**
`jieba` 分词，英文/数字小写化后与中文词一起入索引，`heading + text` 都参与打分，
用 `rank_bm25` 在内存建索引（≤2000 chunk 毫秒级，不持久化，随集合变动懒重建）。
没上 Elasticsearch 是因为知识库规模小、单机演示，内存 BM25 足够且零额外运维。

**Q5：为什么用 LangGraph，不用 ReAct 或纯 prompt 链？**
面试流程是**确定性强状态机**：出题→作答→评估→（追问 | 下一题）→报告，分支条件都能枚举。
用 ReAct 让模型自由选下一步会发散、不可复现、难测试；用纯 prompt 链又做不了状态持久化和条件分支。
LangGraph 给的是显式节点 + 条件边 + 状态快照：可控、可单测（每个节点/路由都能测）、还能断点续跑。

**Q6：RAGAS 分数可信吗？有什么坑？**
RAGAS 是 LLM-as-judge，分数依赖评委模型、prompt 与语言，**绝对值不能当真理**，
只能**固定条件做相对比较**（改检索策略前后对比）并结合人工抽检。我踩的坑：
① 0.4.3 仍从 `langchain_community` 的 vertexai 导入，社区版 0.4.2 删了该模块，需固定到 0.4.1；
② judge `max_tokens` 太小会把长答案的陈述抽取截断，导致单元格缺失、均值失真 → 调到 4096；
③ collections 指标只接受 instructor 工厂接口，旧的 `evaluate/aevaluate` 不兼容。
**「自评偏置」怎么回答**：我没有只靠解释，而是做了**异源 judge 交叉验证**——把同一批生成结果同时交给
同源的 `deepseek-chat` 和**另一厂商**的 `Qwen2.5-72B` 各打一遍分，量化 Δ 与逐条一致率（见 §5.3）。
结果是：`faithfulness`/`context_precision`/`context_recall` 换 judge 后 Δ≤0.03、一致率 89%+，
**没有被自评抬高**；但 `answer_relevancy` 自评偏高 0.108、一致率仅 55.6%，
所以这一项的绝对值我**只当趋势信号**，不拿它当卖点。给面试官的是「偏置有多大」的**数字**，不是「我认为没问题」。

**Q7：faithfulness 0.989 但 answer_relevancy 只有 0.895，说明什么？**
faithfulness 高说明「答案里的陈述基本都能由检索上下文推出」——幻觉控制得好；
answer_relevancy 略低说明有些回答**不够切题或偏冗余**（比如把多条资料堆上去、答非所问）。
这是典型的「忠实但不够精炼」，改进方向是压缩上下文、约束回答结构（例如只答问到的点、先给结论），
而不是加大召回。
补充：`answer_relevancy` 对 judge 选择也敏感（自评比异源 judge 高约 0.11，见 §5.3），
所以这个 0.895 我按**相对趋势**看（用于比较不同检索/生成策略），不把它当绝对值宣传。

**Q8：拒答是怎么判定和评测的？怎么避免误拒答？**
题库外诱导题（7 条，如「CEO 星座」「量子纠缠」）要求系统明确说「资料未提及，无法回答」；
系统提示里约束「仅依据材料作答」。评测侧用规则检测答案是否为拒答，但**初版规则把 2 条长而正确的答案
误判为拒答**——原因是关键词命中太宽；收紧后**排除第三人称描述性内容**，并对命中位置加窗口约束。
最终：诱导题拒答率 100%，非诱导题误拒答率 0%。

**Q9：状态持久化和断点续跑怎么做的？**
每轮图执行结束把 `InterviewState` 快照存 SQLite（会话 ID 为键）。恢复时优先 `restore`：
有快照就续跑原状态，没有（创建后未开始）才按会话元数据 `create` 新建。
前端断线重连只需 `GET /sessions/{id}` 拿回会话与消息，就能接着面。

**Q10：性能和成本怎么优化？**
已落地一项：**语义缓存**——面试出题查询在同会话内恒定，命中即跳过「改写 + 召回 + 精排 + 自评」，
实测 `ask_question` 9194→3182ms（-65.4%）、单场 43.65→25.84s（-40.8%）、成本 -28.7%（见 §5.6）。
仍可做的方向：① 把 rerank 候选数与 Top-K 按需下调；② 用便宜模型做改写/自评、强模型做出题/评分（模型分级）；
③ prompt 压缩 + 只喂必要上下文；④ 流式输出降低首字节等待（SSE 已实现，日志里有 `first_event_ms`）。

**Q11：你怎么衡量「检索质量」和「引用质量」？**
我一开始用的是二值「来源命中率」（召回里有一个是期望来源就算命中），结果**所有档位都是 100%**：
它饱和了，区分不了策略，也回答不了「召回的证据是否精准」。所以我把它升级成**来源粒度 P/R/F1**——
升级后立刻**暴露出原来被 100% 掩盖的问题**：JD 类问题 P 只有 0.5，因为 JD 问题只把中文 JD 当期望来源，
而检索会同时召回同一份 JD 的英文版。
这里有个**要主动坦白的关键点**：JD 的 P=0.5 **不代表检索错**，而是「单文件期望集」把跨文件但合法的召回
判成了非期望——**新指标的副作用就是会暴露口径问题**。改进方向是允许同题多文件或用品级相关度，
我在文档里如实标注了这个局限，没有粉饰。
另外我还量了「答案显式引用标记率」，实测只有 **22.2%**，说明我的生成结果**基本不做行内引用**，
所以我不会把它叫「citation accuracy」（那是过度声称）；引用质量我只能在**检索侧**度量，并明确说清口径。

**Q12：你的评测指标可信度怎么保证？（除了自评偏置）**
三件事：① **固定条件**——judge 模型、`temperature=0`、`max_tokens=4096` 都锁定，只做相对比较；
② **量化偏置**——用异源 judge 交叉验证（§5.3）给出 Δ 和一致率，而不是口头保证；
③ **主动标注局限**——饱和的指标、受 judge 影响大的指标、单期望来源造成的口径偏差，全部写进报告和文档，
不把有问题的数字当卖点。面试时我更愿意讲「这个指标我不敢怎么用」，而不是堆一串好看的数字。

**Q13：评测结果怎么保证不是「跑完就忘」？**
靠**门禁**：把阈值固化成脚本（`check_eval_gate.py`）接进 CI——门槛指标、诱导题拒答率、执行失败样例、
相对基线跌幅，任一项跌出即**非零退出、构建失败**（实测：正常报告退出码 0；把容忍度收到 `--max-drop 0.001`
立刻抓到 `context_recall 1.000→0.993`，用退出码 2 拦下）。但我**没让 CI 重跑 RAGAS**：那要密钥、花真钱、
约 7 分钟还受 TPM 限速。我把评测当**发布前手动步骤**，CI 只对**已入库报告**做秒级、无密钥、可复现的**校验**——
这是「确定性 + 可控成本」优先于「CI 里什么都跑」的取舍。

**Q14：语义缓存怎么保证「命中即等价于重跑」、又不会返回过期结果？**
三个机制：① **命中阈值收紧到余弦 0.95**，只对「几乎完全相同」的查询命中，宁可不命中也不给近似答案；
② 缓存的是**整包检索结果**（`AdaptiveResult` 做 `asdict` 无损序列化往返，有单测断言 `from_dict` 与原件相等），
所以命中就是**重放同一次检索**，不是「重新跑一次近似检索」；③ 两道失效防线——**TTL 1800s** +
**知识库摄入/上传后自动清空缓存**，避免「知识库变了但缓存还在答旧内容」。
另外 `scope`（`kb_types|top_k`）作为过滤条件，**不同检索范围不互相污染**；`SEMANTIC_CACHE_ENABLED` 可运行时开关，
方便做「同环境 A/B」而不是拿两台机器比。实测命中率 0.778（14/18），4 次未命中对应 4 个不同 track 首次出现。
